# Комбинированный пилот: карта плана и порядок работы

Версия документа: 1.3. Дата обновления: 2026-10-06. Исследование: комбинированный верификационный пилот.

Этот пакет фиксирует подробный план комбинированного пилота и последующей сборки продукта. Нулевой шаг — сохранение договорённостей — выполнен. [Первая публичная версия документации](https://xerz.github.io/evaluation-design/combined-pilot/index.html) опубликована, задача PUB-01 завершена: [публичные исходники и правила сборки](../../db-viewer/combined-pilot/README.md). Первый проход аудита сохранён в [audit/README.md](audit/README.md); Eval-2024 идентифицирован и минимально доработан. Проверка реального бота/двух записей, полное научное основание, новая БД, MODEUS и трёхминутный HTML ещё предстоят.

Рабочие документы остаются источником решений; публичные Markdown в `db-viewer/combined-pilot/content/` — отредактированное производное без локальных путей, внутренних служебных ID и операционных выгрузок. При изменениях обновлять обе версии и проверять сайт. Контрольные суммы каталога исходников ниже относятся к фиксации 1.0; изменение сборщика для PUB-01 отражено в журнале и Git.

## С чего начинать

1. Прочитать этот README: он объясняет структуру и источники.
2. Открыть [08-workplan-and-decisions.md](08-workplan-and-decisions.md): найти текущие задачи, зависимости и открытые решения.
3. Для выбранной задачи прочитать тематический файл и указанные первичные материалы.
4. Проверить принятые решения и ограничения перед изменениями. Договорённости пользователя в текущем чате имеют приоритет над историческим дизайном и высказываниями в PDF.
5. Выполнить задачу, приложить свидетельство проверки, обновить её статус и затронутые документы.

## Правила ведения

- У задач устойчивые ID: DOC, PROD, CRIT, LIT, EXP, TECH, SAMPLE, ANN, DATA, WEB, PRES, PUB, TOOL. Их нельзя переиспользовать для другого смысла. Детали находятся в одном тематическом файле; общий список ссылается на них.
- Принятые решения имеют ID D-xx, дату и основание. Гипотезы маркируются отдельно: они не превращаются в решения или результаты после переноса в БД. Открытые вопросы имеют ID Q-xx; вопрос не считается закрытым по умолчанию.
- Статусы задач: `todo`, `in_progress`, `waiting_for_decision`, `done`. `done` требует конкретного результата и проверки. Ни один этап исследования не считается выполненным только по этому плану.
- Ответственный указывается лишь после назначения. В начале пакета ответственные не назначены; роли и упоминания участников в PDF не являются назначениями от пользователя.
- Markdown хранит замысел, решения и подробные процедуры. Исследовательская БД хранит формализованные критерии, условия, научные связи и операционные записи. Pages, SQL-снимки, таблицы, ERD и презентационные выгрузки производны от согласованной версии.
- Каждый вопрос подробно описывается в одном файле. В остальных документах используются ссылки на его ID. Сводные таблицы допустимы, но не заменяют подробную процедуру.
- При изменении решения сначала записать его дату, основание и затронутые ID в журнал. Обновить тематический документ и зависимости задач, затем формализованную модель и производные артефакты. Зафиксировать версию, проверку и необходимость повторного анализа.
- Для исходной рубрики, записей и результатов сохранять происхождение. При работе с памятью, PDF-резюме, историческими статьями или прежними интерфейсными снимками не приписывать источнику текущую техническую готовность или доказанную валидность.
- Порог успеха, объём основной разметки, очное наблюдение и окончательная комплектация остаются открытыми до соответствующего решения. Форма на 26 критериев допускает недостаточность данных.
- Ветка пакета — `codex/combined-pilot-plan`. Исходная main-копия с существующими локальными изменениями сохранена. Пакет расположен вне `docs/`, который сборщик полностью заменяет.

Это порядок тематических блоков, а не требование завершить DATA до подготовки выборки. Фактический порядок завершения определяется зависимостями задач в файле 08: проба и решение о протоколе нужны для окончательной DATA-01. Аудит техники и предварительное проектирование сцен можно вести параллельно с формализацией, но публикуемые факты должны соответствовать согласованной версии. Первый цикл на восьми занятиях не является самостоятельным доказательством пригодности продукта для всех университетов.
